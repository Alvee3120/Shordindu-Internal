# Decisions

- Weekend: Friday only (editable setting)
- Assignment due date: optional
- Assignments visible to everyone
- Users on leave still receive assignment emails, with an 'On leave' flag
- Sessions last 30 days
- Leave: Simple marking only. No approval or cancellation flow; users mark themselves on leave, Managers/HR/Admin can mark for others.
- Mentions: Supported across all rich text (daily updates, assignments, comments). Schema uses target_type and target_id.
- Assignments: Assignees can mark their own status as Done / Complete (with optional note).
- Login: email + password (not passwordless). Registration sets the password and verifies email ownership with an OTP. Minimum password length 8.
- Password reset: self-service through an emailed OTP.
- The seeded first Admin starts without a password and sets one through the forgot-password flow.
- Permissions changed from the original table: weekdays/weekend setting, holidays, and departments/reminder-time settings are managed by Manager, HR and Admin (not HR/Admin or Admin-only). Audit log, the Admin-role grant, and Admin accounts remain Admin-only.
- Announcements: a notice board visible to everyone. Admin, HR and Manager can post, edit and delete. Posting queues one email per other Active user immediately (not batched in the digest). Same-day edit lock, soft delete, and audit logging apply.
- Group chat: one global room, not person-to-person. Any signed-in user can post. Plain text with @mentions (reusing the comment mention format). Mentions notify the mentioned person only; chat messages are not emailed. Same-day edit/delete lock, soft delete, and audit logging apply. Client polls every 5 seconds and pages older messages backwards.
- Chat unread badge: a floating button pinned bottom-right links to the chat and shows how many messages were posted since the user last opened the room. Tracked with a `ChatRead.lastReadAt` marker per user; own and soft-deleted messages never count. Polled every 30 seconds; cleared on opening the room.
- Chat live sync: the poller asks for everything changed after an `(updatedAt, id)` cursor, not just new messages, so edits and deletions appear for other users without a reload. Deletions come back as id-only tombstones. Write stamps are bumped by at least 1ms (`nextChangeStamp`) so two changes in the same millisecond cannot be skipped.
- Leave is a request/approval flow (supersedes "simple marking only" above). A user applies with a date range and a reason; the request starts Pending. Manager, HR and Admin approve or reject, and the row records who decided (`decidedBy`) and when. Only Approved leave marks the person as on leave for the day (not-submitted list and reminders). An approver cannot decide their own request. An approver marking leave directly for someone else is Approved immediately, since the marking is the decision. Existing pre-flow rows were grandfathered as Approved. Leave has no category field.
- Personal calendar: each user has "My Calendar". It shows their own entries (title, optional notes, one whole-day date) plus assignment due dates where they are an active, unfinished assignee. Assignments are read from the assignment table, never copied, so a changed due date or a cancelled assignment never leaves a stale entry. Calendar entries are edited or deleted only by their owner; assignment items are read-only on the calendar and link through to the assignment. Reminders for personal entries are emailed at 10:30 Asia/Dhaka on the day itself, marked per entry so a retry never double-sends. Assignments keep their own 9 AM due reminder.
- Profile pictures: images are stored on disk (`.data/avatars`, overridable with `AVATAR_UPLOAD_DIR`), and the database holds only the filename. The server resizes every upload with sharp to a 256x256 WebP, centre-cropped (`fit: "cover"`) to fill the avatar circle, so a 1200x900 photo lands around 24 KB. Client-side size/type checks are a courtesy; the server re-validates type, size and image integrity. Users may change their own display name and picture from /profile; email, department, position and role stay Admin-managed.
- Email is split across two provider accounts (Brevo free tier is 300/day). The **auth** account sends only mail a user needs to sign in: register/reset OTP, invite, approval, rejection. Everything else — daily/assignment/calendar reminders, notification digests, announcements — goes through the **bulk** account, so a reminder burst can never starve sign-in mail. Both accounts are configured with `SMTP_AUTH_*` and `SMTP_BULK_*`, falling back to `SMTP_USER`/`SMTP_PASS` for single-account setups.
- Daily caps are enforced per account, counted on the Asia/Dhaka calendar day (`email_account_usage`, atomic `INSERT ... ON CONFLICT` claim). Digests are low priority and leave `EMAIL_LOW_PRIORITY_RESERVE` slots for reminders. When the cap is hit: reminders are skipped with a recorded reason on the `job_runs` row, digests stay unmarked and go out after the reset, and sign-in mail on the auth account has its own 300 that other mail never touches. `smtp`/`resend` failures are classified — an explicit SMTP/HTTP 4xx is retried, but a timeout or dropped connection is never resent (it may already have been delivered) and is dropped to the dead-letter queue instead.
- Reminder runs are retried when a previous attempt left the day's `job_runs` row `failed`; a crashed run no longer permanently marks that day as done. Calendar entries are only marked `remindedAt` when the email actually sent.
